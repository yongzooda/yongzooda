- **스택** · Java 21 · Spring Boot 4 · JPA · MySQL 8.4 · Redis · Flyway · Python · FastAPI · LangChain · LangGraph · OpenAI · AWS ECS Fargate · GitHub Actions · React Native

### 1. 날짜가 바뀐 뒤 첫 요청끼리 부딪히던 데드락 · PR #192

- **문제** 앱을 켜면 홈 화면 요청 두 개가 500. 그중 하나는 날짜가 바뀐 뒤 첫 실행에서만 나서 한동안 재현하지 못함
- **원인** 오늘의 퀴즈 세트를 조회해 보고 없으면 만드는 코드. 자정 뒤 요청이 겹치면 모두 세트가 없다고 보고 각자 새로 넣으려다, 같은 날짜 세트를 막는 유니크 제약에서 서로의 잠금을 기다리며 데드락
- **해결**
  - 세트 생성을 독립 트랜잭션(REQUIRES_NEW)으로 떼고, 중복은 DB 유니크 제약에 맡김. 경합에서 진 요청은 이긴 쪽이 만든 세트를 다시 읽음
  - 처음에 놓쳤던 두 가지도 함께 고침. 읽기 전용 트랜잭션 안에서는 방금 커밋된 세트가 보이지 않아 조회를 NOT_SUPPORTED로 바꾸고, 서버 안 잠금이 트랜잭션 안에 있을 때 동시 요청 10건이 모두 500이 나서 잠금을 트랜잭션 바깥으로 옮김
  - 서버 안 잠금은 서버가 여러 대가 되면 서로 닿지 않아, 기다림을 줄이는 용도로만 사용
  - 홈의 나머지 500은 기기 토큰을 매번 새로 넣다 난 중복 키 오류라, 같은 토큰이 있으면 그 행을 넘겨받게 함께 수정
- **결과** 동시 요청 2·3·5·8건 모두 성공, 데드락 0건, 세트는 매번 한 벌. 12건부터 나는 실패는 커넥션 풀 기본 크기(10)를 넘은 탓이라 따로 기록

### 2. 검토 없이 바뀌던 운영 DB를 Flyway로 전환 · PR #297

- **문제** 운영을 시작하자 main 머지가 곧 운영 배포. 서버가 켜질 때마다 Hibernate가 엔티티에 맞춰 스키마를 고치는 설정(ddl-auto: update)이라, 머지 한 번이면 검토도 기록도 없이 운영 DB 구조가 바뀜. 운영 배포 전 셀프 리뷰에서 운영 위험의 첫 항목으로 적어 둔 문제
- **해결**
  - 운영 배포 이틀 뒤(9월 30일) Flyway로 전환. 지금 엔티티가 만드는 스키마를 기준 버전(V1)으로 두고, 운영 DB 스키마와 같은지 먼저 대조
  - 대조에 쓴 일회성 작업은 잘못 돌면 초기 데이터 덤프를 덮어쓸 수 있어, 실행 전에 명령을 눈으로 확인하는 단계를 배포 런북에 추가
  - 로컬 DB 사본으로 리허설해 51개 테이블, 14,470행이 그대로인 것 확인
  - 팀이 따라 할 수 있게 노션 안내 페이지와 README 규칙 작성
- **결과** 그 뒤로 스키마를 바꾸는 PR에는 마이그레이션 파일이 함께 올라옴. 이 규칙이 한 번 뚫린 일은 아래 3번에 정리

> 9월 30일 저장소 README에 남긴 규칙<br>
> 엔티티를 바꾸면 같은 PR 에 마이그레이션 파일을 넣어야 한다. enum 상수를 추가할 때도 마찬가지다

### 3. 16일 동안 조용히 실패하던 완성 알림 · PR #410

- **문제** 약점 분석표가 완성돼도 완성 알림이 저장되지도 발송되지도 않음. 분석표는 정상으로 끝나서 겉으로는 드러나지 않음
- **원인** 알림 종류 두 개를 추가한 PR이 마이그레이션 없이 합쳐졌고, 10월 22일 직접 낸 릴리스에 실려 운영에 나감. MySQL enum 컬럼에 그 값이 없어 저장하는 순간 실패
  - 10월 8일 셀프 리뷰에 그 누락을 적어 두고도 해당 PR에 알리지 않았고, 릴리스에서도 걸러 내지 못함
- **16일 동안 몰랐던 이유**
  - 서버가 켜질 때 하는 스키마 검사는 enum 값 목록까지 비교하지 않음
  - 테스트는 엔티티로 매번 새로 만드는 H2에서 돌아 차이가 생길 수 없음
  - 알림 코드는 예외를 로그로만 남겼는데 그 로그를 보는 알람이 없음
- **해결** 11월 7일 빠진 값을 넣는 마이그레이션(V13) 작성, 다른 enum 매핑 45개도 실제 스키마와 전부 대조. 배포가 실패하면 서버만 이전 버전으로 돌아가고 DB는 그대로 남아서, 고치기 전 버전의 서버가 새 스키마에서도 뜨는지 확인한 뒤 배포
- **남은 것** 재발을 막는 검사(기동 시 enum 대조, 마이그레이션 SQL 검사 테스트, 로그 알람)는 제안만 하고 아직 넣지 못함. 로그가 남아 있던 기간에 확인된 실패는 1건

## 기술 선택 이유

| 선택 | 이유 |
| :-- | :-- |
| Flyway | ddl-auto: update로는 운영 DB 구조가 검토도 기록도 없이 바뀜 |
| MySQL 8.4 | 8.0은 2026년 7월 31일 표준 지원이 끝나 새로 만들면 연장 지원 비용이 붙음 |
| ECS Fargate Spot | 서버 태스크를 온디맨드로 돌리면 한 달에 24.5달러, Spot은 7\~10달러. AWS가 회수하면 1\~2분 끊길 수 있어 시연 날 온디맨드로 바꾸는 절차를 런북에 정리 |
| NAT 게이트웨이 없이 퍼블릭 서브넷 | NAT 게이트웨이는 한 달에 40달러가 넘음. 대신 보안 그룹은 ALB에서 오는 8080 포트만 허용 |
| GitHub OIDC | 액세스 키를 저장소에 두지 않고, 배포 역할은 이 저장소의 main 브랜치에서만 쓰게 제한 |
| CloudFront 기본 인증서 | 도메인 없이 HTTPS 적용. ALB에는 공인 IP를 주지 않고 CloudFront에서 오는 요청만 받음 |
| DB는 비공개 서브넷, 비밀값은 Parameter Store | 7월에 밖으로 열려 있던 로컬 개발용 DB가 외부 봇에 지워진 일(잃은 것은 더미 데이터뿐)을 운영 설계에 반영 |
| 약점 점수는 서버가, 해석만 AI가 | 약점 후보와 점수는 서버 규칙이 정하고 AI는 바꿀 수 없음. 근거가 모자란 요청에는 AI를 부르지 않고 코인도 받지 않음. AI에는 문제 원문이나 개인정보 대신 근거 번호와 오개념 코드만 전달 |
| 문항 생성·검수 모델 gpt-5.4 | 네트워크 과목 비교에서 gpt-5.5보다 교재 근거 부족 비율이 낮고(11.5% 대 19.0%) 검수 통과율이 높았으며(62.8% 대 54.7%) 비용은 약 3분의 1. gpt-5.4-mini보다 비싸지만 정답 정확성과 해설이 나음 |

## 아직 못 한 것

- Redis가 태스크 안에 떠 있어 태스크를 하나로 고정. 둘로 늘리면 인증번호 확인과 정기 알림의 스케줄 락이 어긋나서, 늘리려면 Redis부터 ElastiCache로 옮겨야 함
