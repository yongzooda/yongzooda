## 한 줄 요약

여행상품 일정표를 한국관광공사 관광정보와 대조해 출시 전에 문제를 짚어 주는 검수 서비스. 검수 엔진과 API 서버 대부분, 외부 API 연동, CI와 배포·운영을 맡음

- **서비스** · 규칙 10가지 일정 검수(쉬는 날·운영시간, 행사 기간, 이동 시간, 날씨 등), 판정 근거와 수정안, 출시 준비도 점수, 출시 뒤 관광정보 변경 알림
- **담당** · 검수 엔진 · TourAPI·카카오모빌리티·기상청 연동과 하루 호출 예산 · 변경 감지 배치 · 검수 리포트 PDF · 접근 통제와 로그인 잠금 · 웹 화면 작업 · CI · Railway 배포와 자동 재배포
- **스택** · TypeScript · NestJS · PostgreSQL · Next.js · GitHub Actions · Railway · Claude API
- **링크** · [저장소](https://github.com/tourlint/tourlint) · [서비스](https://tourlint-web.up.railway.app)

### 1. 외부 API에 못 닿는 서버가 배포 검사를 통과한 장애 · PR #701, #759

- **문제** 1차 심사 자료 제출 마감일이던 9월 21일, 새로 뜬 API 컨테이너 다섯 개 중 두 개가 관광공사 API에 아예 연결되지 않음. 헬스체크(/health)는 인증키가 있는지만 보고 200을 돌려줘서 Railway가 그 컨테이너로 트래픽을 넘김. 그때마다 4분쯤 장소 검색과 검수가 503
- **해결**
  - 서버가 켜질 때 관광공사 API를 미리 한 번 불러 보고, 닿기 전까지는 /health가 503을 돌려주게 변경. 배포 검사를 통과하지 못하니 그동안에는 기존 컨테이너가 계속 트래픽을 받음
  - 미리 부르기가 실패하면 20초 간격으로 15번, 그 뒤로는 10분 간격으로 재시도. 시간 초과도 하루 호출 예산에 잡혀서 간격을 벌림
  - 다음 날 실패한 컨테이너의 네트워크 흐름 로그를 보니 관광공사로 연결 요청 107번, 응답 0번. 같은 이미지를 다시 띄우는 것 말고는 살릴 방법이 없어서, 배포 감시 워크플로에 검사에서 떨어진 배포를 같은 이미지로 세 번까지 다시 띄우는 단계 추가
- **결과** 9월 22일 16시 35분 머지, 16시 39분 배포가 검사에서 떨어짐, 16시 47분 자동으로 다시 떠서 1분 만에 복구
- **남은 것** 관광공사 쪽이 일부 발신 IP를 받지 않는다는 데까지 좁혔지만 이유는 확정하지 못함. 지금 해결은 우회책

### 2. 첫 수정이 문제를 옮기기만 한 검수 점수 오류 · PR #437, #440, #448

- **문제** 시연 상품을 운영에서 검수하니 26점, 명세의 기대값은 29점. 이미 「끝난 행사」로 차단된 축제에 「휴무일 확인 불가」가 또 붙어 점수가 두 번 깎임
- **첫 수정** 축제는 관광공사 데이터에 휴무일 칸이 아예 없어서 휴무 판정만 건너뛰게 고침. 그런데 배포 뒤 다시 검수해도 26점. 다음 단계인 운영시간 판정에서 같은 등급의 확인 불가가 났기 때문
  - 단위 테스트에는 파서가 읽을 수 있는 「10:00\~18:00」을 넣었지만, 실제 값은 「평일 13:00\~18:00(주말 11:00\~18:00 *벚꽃길은 상시 개방)」
- **다시 고침** 축제를 운영시간 규칙에서 통째로 뺌(개최 기간은 다른 규칙이 봄). 잘못된 동작을 지키던 앞 PR의 테스트는 지우고, 운영의 실제 문구를 그대로 쓰는 테스트를 새로 작성. 운영 재검수에서 29점 확인
- **재발 방지** 기대값 표의 점수를 통째로 대조하는 회귀 테스트 추가. 고친 걸 되돌리면 이 테스트가 실패해서, 운영 화면을 보고서야 찾던 오류를 이제 로컬에서 잡음

### 3. 되돌려도 통과하던 테스트와 그 뒤 만든 검증 규칙 · commit 2304594

- **문제** 수정안 확정 기능에 넣은 가드 12개를 고치기 전 코드로 하나씩 되돌려 보니, 3개는 테스트가 그대로 통과. 테스트 데이터 순서가 우연히 경계를 밟지 않았거나, 검사가 아예 없었거나, 조건이 틀려 있었음
- **해결**
  - 팀 규칙집에 「검증」 장을 새로 작성. 새 가드는 되돌려서 실패하는지 보고, 그래도 통과하면 가드가 아니라 테스트를 의심
  - 실제로 나온 원인 세 가지(테스트 데이터가 경계를 밟지 않음, 비교하는 두 값이 맞닿아 있지 않음, 다른 장치가 대신 막아 줌)를 함께 기록
  - PR 템플릿에 「가드를 새로 넣었으면 되돌려 실패하는지 확인하고 그 결과를 적는다」 항목 추가
- **결과** 같은 방법으로 엔진, API, 배치, 검수 쪽에서 되돌려도 안 걸리던 가드를 더 찾아 검사를 보탬. 그 뒤 만든 LLM 보완 기능의 안전장치 4개도 하나씩 되돌려 모두 실패하는 것 확인

## 기술 선택 이유

| 선택 | 이유 |
| :-- | :-- |
| 규칙 엔진은 순수 함수 | 규칙 안에서 외부를 부르면 같은 입력에 같은 결과가 보장되지 않아 검수 결과가 근거가 될 수 없음. 엔진이 외부 API나 저장소 코드를 가져오면 eslint에서 막힘 |
| AI는 정규화까지 | AI가 판정하면 같은 상품을 두 번 검수했을 때 결과가 달라짐. 규칙 파서가 휴무일 문장의 95.8%, 운영시간 문장의 91.7%를 읽어서, LLM은 파서가 못 읽은 조각에만 쓰고 파서가 읽은 값은 덮어쓰지 못하게 함 |
| LLM 결과는 조각별 캐시 | temperature 0도 매번 같은 답을 보장하지 않아서, 「같은 상품을 세 번 검수하면 문구까지 같아야 한다」는 기준을 캐시로 지킴 |
| 형식이 어긋난 LLM 답은 통째로 버림 | 휴무일을 잘못 읽으면 멀쩡한 일정이 차단됨 |
| 「확인 불가」 등급 | 운영시간 정보가 없는 곳을 정상으로 넘기지 않음. 외부 조회가 실패해도 그 관광지나 그 구간만 확인 불가로 두고 검수는 끝까지 진행 |
| 서비스 전체 하루 호출 예산 | 자동 배치가 한도에 닿기 전에 먼저 멈춰, 사용자가 누르는 검수에 쓸 호출을 남김 |
| 오류 종류별 재시도 | 일시적인 오류는 간격을 늘려 다시 부르고, 인증 오류나 한도 초과처럼 재시도해도 소용없는 오류는 바로 멈춤 |
